## The Slice Compiler for C++

The Slice-to-C++ compiler (`slice2cpp`) offers the following additional options:

### `--header-ext` `EXT`

Changes the file extension for the generated header files from the default `h` to the extension specified by `EXT`.

You can also change the header file extension with a global metadata directive:

```slice
[["cpp:header-ext:hpp"]]

// ...
```

Only one such directive can appear in each source file. If you specify a header extension on both the command line and
with a metadata directive, the metadata directive takes precedence. This ensures that included Slice files that were
compiled separately get the correct header extension (provided that the included Slice files contain a corresponding
metadata directive). For example:

```slice
// File example.ice
#include <Ice/BuiltinSequences.ice>

// ...
```

Compiling this file with

```shell
slice2cpp --header-ext=hpp -I/opt/Ice/include example.ice
```

generates `example.hpp`, but the `#include` directive in that file is for `Ice/BuiltinSequences.h` (not
`Ice/BuiltinSequences.hpp`) because `BuiltinSequences.ice` contains the metadata directive `[["cpp:header-ext:h"]]`.

You normally will not need to use this metadata directive. The directive is necessary only if:

- You `#include` a Slice file in one of your own Slice files.
- The included Slice file is part of a library you link against.
- The library ships with the included Slice file's header.
- The library header uses a different header extension than your own code.

For example, if the library uses `.hpp` as the header extension, but your own code uses `.h`, the library's Slice file
should contain a `[["cpp:header-ext:hpp"]]` directive. (If the directive is missing, you can add it to the library's
Slice file.)

### `--source-ext` `EXT`

Changes the file extension for the generated source files from the default `cpp` to the extension specified by `EXT`.

### `--add-header HDR[,GUARD]`

This option adds an include directive for the specified header at the beginning of the generated source file (preceding
any other include directives). If `GUARD` is specified, the include directive is protected by the specified guard. For
example, `--add-header precompiled.h,__PRECOMPILED_H__` results in the following directives at the beginning of the
generated source file:

```cpp
#ifndef __PRECOMPILED_H__
#define __PRECOMPILED_H__
#include <precompiled.h>
#endif
```

The option can be repeated to create include directives for several files.

As suggested by the preceding example, this option is useful mainly to integrate the generated code with a compiler's
precompiled header mechanism.

### `--include-dir DIR`

Prepends the directory `DIR` to the path in the `#include` directive that the generated source file uses to include its
own header file.

## Include Directives

The `#include` directives generated by the Slice-to-C++ compiler can be a source of confusion if the semantics governing
their generation are not well-understood. The generation of `#include` directives is influenced by the command-line
options `-I` and `--include-dir`; these options are discussed in more detail below. The `--output-dir` option directs
the translator to place all generated files in a particular directory, but has no impact on the contents of the
generated code.

Given that the `#include` directives in header files and source files are generated using different semantics, we
describe them in separate sections.

### Header Files

In most cases, the compiler generates the appropriate `#include` directives by default. As an example, suppose file
`A.ice` includes `B.ice` using the following statement:

```slice
// A.ice
#include <B.ice>
```

Assuming both files are in the current working directory, we run the compiler as shown below:

```shell
slice2cpp -I. A.ice
```

The generated file `A.h` contains this `#include` directive:

```cpp
// A.h
#include <B.h>
```

If the proper include paths are specified to the C++ compiler, everything should compile correctly.

Similarly, consider the common case where `A.ice` includes `B.ice` from a subdirectory:

```slice
// A.ice
#include <inc/B.ice>
```

Assuming both files are in the `inc` subdirectory, we run the compiler as shown below:

```shell
slice2cpp -I. inc/A.ice
```

The default output of the compiler produces this `#include` directive in `A.h`:

```cpp
// A.h
#include <inc/B.h>
```

Again, it is the user's responsibility to ensure that the C++ compiler is configured to find `inc/B.h` during
compilation.

Now let us consider a more complex example, in which we do not want the `#include` directive in the header file to match
that of the Slice file. This can be necessary when the organizational structure of the Slice files does not match the
application's C++ code. In such a case, the user may need to relocate the generated files from the directory in which
they were created, and the `#include` directives must be aligned with the new structure.

For example, let us assume that `B.ice` is located in the subdirectory `slice/inc`:

```slice
// A.ice
#include <slice/inc/B.ice>
```

However, we do not want the `slice` subdirectory to appear in the `#include` directive generated in the header file,
therefore we specify the additional compiler option `-Islice`:

```shell
slice2cpp -I. -Islice slice/inc/A.ice
```

The generated code demonstrates the impact of this extra option:

```cpp
// A.h
#include <inc/B.h>
```

As you can see, the `#include` directives generated in header files are affected by the include paths that you specify
when running the compiler. Specifically, the include paths are used to abbreviate the path name in generated `#include`
directives.

When translating an `#include` directive from a Slice file to a header file, the compiler compares each of the include
paths against the path of the included file. If an include path matches the leading portion of the included file, the
compiler removes that leading portion when generating the `#include` directive in the header file. If more than one
include path matches, the compiler selects the one that results in the shortest path for the included file.

For example, suppose we had used the following options when compiling `A.ice`:

```shell
slice2cpp -I. -Islice -Islice/inc slice/inc/A.ice
```

In this case, the compiler compares all of the include paths against the included file `slice/inc/B.ice` and generates
the following directive:

```cpp
// A.h
#include <B.h>
```

The option `-Islice/inc` produces the shortest result, therefore the default path for the included file
(`slice/inc/B.h`) is replaced with `B.h`.

In general, the `-I` option plays two roles: it enables the preprocessor to locate included Slice files, and it provides
you with a certain amount of control over the generated `#include` directives. In the last example above, the
preprocessor locates `slice/inc/B.ice` using the include path specified by the `-I.` option. The remaining `-I` options
do not help the preprocessor locate included files; they are simply hints to the compiler.

Finally, we recommend using caution when specifying include paths. If the preprocessor is able to locate an included
file via multiple include paths, it always uses the first include path that successfully locates the file. If you intend
to modify the generated `#include` directives by specifying extra `-I` options, you must ensure that your include path
hints match the include path selected by the preprocessor to locate the included file. As a general rule, you should
avoid specifying include paths that enable the preprocessor to locate a file in multiple ways.

### Source Files

By default, the generated source file includes its own header file with an `#include` directive that uses only the base
name of the header file. This behavior is usually appropriate when the source file and header file reside in the same
directory.

For example, suppose `A.ice` includes `B.ice` from a subdirectory, as shown in the following snippet of `A.ice`:

```slice
// A.ice
#include <inc/B.ice>
```

We generate the source file using this command:

```shell
slice2cpp -I. inc/A.ice
```

Upon examination, we see that the source file contains the following `#include` directive:

```cpp
// A.cpp
#include "A.h"
```

The `#include` directive for `B.h` appears in `A.h`, as described in [Header Files](#header-files).

However, suppose that we wish to enforce a particular standard for generated `#include` directives so that they are
compatible with our C++ compiler's existing include path settings. In this case, we use the `--include-dir` option to
modify the generated code. For example, consider the compiler command shown below:

```shell
slice2cpp --include-dir src -I. inc/A.ice
```

The source file now contains the following `#include` directive:

```cpp
// A.cpp
#include "src/A.h"
```

The directive still omits the directory of the Slice file, `inc`.

## Using Ice with CMake

Ice for C++ ships with a CMake package that defines an imported library target for each Ice library, such as `Ice::Ice`
and `Ice::IceGrid`, and the `slice2cpp_generate` function, which compiles the Slice files of a target as part of the
build. For example:

```cmake
cmake_minimum_required(VERSION 3.21)
project(greeter CXX)

find_package(Ice REQUIRED CONFIG)

add_executable(client Client.cpp Greeter.ice)
slice2cpp_generate(client)
target_link_libraries(client PRIVATE Ice::Ice)
```

The package requires CMake 3.21 or later. The `CONFIG` keyword makes `find_package` use config mode: it loads the
package configuration file that Ice for C++ provides, rather than the `FindIce` find module that ships with CMake.
Config mode is what CMake recommends for a project that provides its own package configuration
([cmake-packages(7)](https://cmake.org/cmake/help/latest/manual/cmake-packages.7.html)).

If you installed Ice in a directory that CMake does not search by default, such as `/opt/Ice`, add that directory to
`CMAKE_PREFIX_PATH`. On Windows, Ice for C++ is a NuGet package; see [Windows](#windows).

`slice2cpp_generate(client)`:

- compiles each Slice file in the sources of `client` with `slice2cpp`, and adds the generated header and source files
  to the target's sources;
- adds the directory of the generated headers to the target's include directories, so `Client.cpp` can
  `#include "Greeter.h"`;
- passes `Ice_SLICE_DIR`, the directory of the Ice Slice files, to `slice2cpp` with `-I`, so
  `#include <Ice/Identity.ice>` resolves;
- records the Slice files that each Slice file includes in a dependency file, so the build compiles a Slice file again
  when it, or a file it includes, changes.

Call `slice2cpp_generate` in the same `CMakeLists.txt` as the `add_executable` or `add_library` call that creates the
target, after that call lists the target's Slice files.

### Imported Targets

`find_package` defines an imported library target for each Ice library in the installation:

| Library             | Imported target             |
| ------------------- | --------------------------- |
| Ice                 | `Ice::Ice`                  |
| DataStorm           | `Ice::DataStorm`            |
| Glacier2            | `Ice::Glacier2`             |
| IceBox              | `Ice::IceBox`               |
| IceDiscovery        | `Ice::IceDiscovery`         |
| IceGrid             | `Ice::IceGrid`              |
| IceLocatorDiscovery | `Ice::IceLocatorDiscovery`  |
| IceStorm            | `Ice::IceStorm`             |
| IceBT               | `Ice::IceBT`, on Linux only |

Each target adds the Ice include directory, requires C++17, and links the Ice libraries that its library depends on, so
a target that links `Ice::IceGrid` also links `Ice::Glacier2` and `Ice::Ice`.

To make `find_package` fail when a library is missing from the installation, list it as a component:

```cmake
find_package(Ice REQUIRED CONFIG COMPONENTS IceGrid IceStorm)
```

The package also defines two imported executables: `Ice::slice2cpp`, the Slice compiler that `slice2cpp_generate` runs,
and, on Windows, `Ice::icebox_EXE`, the IceBox server from the NuGet package. `Ice::icebox_EXE` resolves to the Debug
`icebox.exe` in the Debug configuration and to the Release `icebox.exe` in every other configuration, like the Ice
libraries. A custom command that runs `slice2cpp` uses `$<TARGET_FILE:Ice::slice2cpp>` in its `COMMAND` and `DEPENDS`,
so it runs again when the compiler changes.

### Windows

On Windows, Ice for C++ is the `ZeroC.Ice.Cpp` NuGet package. Restore the package, then set `Ice_ROOT` to its directory
before calling `find_package`:

```shell
nuget install ZeroC.Ice.Cpp -Version 3.8.3 -OutputDirectory packages
```

```cmake
set(Ice_ROOT "${CMAKE_CURRENT_SOURCE_DIR}/packages/ZeroC.Ice.Cpp.3.8.3")
find_package(Ice REQUIRED CONFIG)
```

The package contains Debug and Release libraries for the `x64` and `Win32` platforms. The Debug configuration links the
Debug libraries, and every other configuration links the Release libraries. The `Ice_WIN32_PLATFORM` cache variable
selects the platform; it defaults to `x64` in a 64-bit build and to `Win32` in a 32-bit build.

The Ice DLLs stay in the package directory, so copy them next to the executable to run it from the build directory.
`$<TARGET_RUNTIME_DLLS:client>` lists the DLLs of the Ice libraries that `client` links, and the `ICE_RUNTIME_DLLS`
property of `Ice::Ice` lists the other DLLs that Ice loads, such as the bzip2 DLL:

```cmake
if(WIN32)
  add_custom_command(TARGET client POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy
      $<TARGET_RUNTIME_DLLS:client>
      $<GENEX_EVAL:$<TARGET_PROPERTY:Ice::Ice,ICE_RUNTIME_DLLS>>
      $<TARGET_FILE_DIR:client>
    COMMAND_EXPAND_LISTS
  )
endif()
```

### `slice2cpp_generate` Arguments

| Argument                                             | Description                                                                                                                   |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `INCLUDE_DIRS <dir>...`                              | Directories to search for included Slice files, passed to `slice2cpp` with `-I`.                                              |
| `OPTIONS <option>...`                                | Other `slice2cpp` options, such as `-D` or `--header-ext`.                                                                    |
| `HEADER_OUTPUT_DIR <dir>`                            | The directory for the generated headers, instead of the default under the build directory.                                    |
| `INCLUDE_DIR <dir>`                                  | The include prefix of the generated headers, passed to `slice2cpp` with `--include-dir`.                                      |
| `INCLUDE_SCOPE PRIVATE\|PUBLIC`                      | With `PUBLIC`, the targets that link this target also get the directories of the generated headers. The default is `PRIVATE`. |
| `DEPENDS <dep>...`                                   | Other files whose changes recompile the Slice files.                                                                          |
| `GENERATED_HEADERS <var>`, `GENERATED_SOURCES <var>` | Variables that receive the paths of the generated headers and sources.                                                        |

### Generated Files

By default, `slice2cpp_generate` writes the files it generates for a target under `generated/<target>` in the current
binary directory, `CMAKE_CURRENT_BINARY_DIR`.

Within this directory, `slice2cpp_generate` keeps the Slice file's path relative to the `INCLUDE_DIRS` directory that
contains it. For example, with `INCLUDE_DIRS ${CMAKE_CURRENT_SOURCE_DIR}/slice`, the Slice file `slice/Demo/Weather.ice`
generates `Demo/Weather.h` and `Demo/Weather.cpp` under `generated/<target>`. This is the path that `slice2cpp` uses in
the `#include` directives it generates for that file: the `#include <Demo/Weather.ice>` directive of another Slice file
becomes `#include <Demo/Weather.h>` in its generated header (see [Header Files](#header-files)). A Slice file outside
the `INCLUDE_DIRS` directories generates its files directly in `generated/<target>`.

Use `HEADER_OUTPUT_DIR` to choose the directory for the generated headers, which keep their relative paths. A relative
`HEADER_OUTPUT_DIR` starts at `CMAKE_CURRENT_BINARY_DIR`. The generated sources stay in `generated/<target>`. Use
`INCLUDE_DIR` to add a subdirectory beneath the header directory; each generated source then includes its header through
this subdirectory. For example:

```cmake
add_library(weather_api Weather.ice)
slice2cpp_generate(weather_api
  HEADER_OUTPUT_DIR ${CMAKE_BINARY_DIR}/include
  INCLUDE_DIR Demo)
target_link_libraries(weather_api PUBLIC Ice::Ice)
```

This call generates `${CMAKE_BINARY_DIR}/include/Demo/Weather.h` and `Weather.cpp` in `generated/weather_api`, and
`Weather.cpp` includes its header with `#include "Demo/Weather.h"`.

### Sharing Generated Headers Between Targets

Set `INCLUDE_SCOPE PUBLIC` so that targets that link your library can include its generated headers.

`slice2cpp_generate` compiles only the Slice files listed in the target's sources; `INCLUDE_DIRS` only lets `slice2cpp`
find the Slice files that they include. Compile a Slice file shared by several targets in a separate library, and link
that library from each target that uses it:

```cmake
add_library(demo_common ../slice/Demo/Common.ice)
slice2cpp_generate(demo_common
  INCLUDE_DIRS ${CMAKE_CURRENT_SOURCE_DIR}/../slice
  HEADER_OUTPUT_DIR ${CMAKE_BINARY_DIR}/include
  INCLUDE_SCOPE PUBLIC)
target_link_libraries(demo_common PUBLIC Ice::Ice)

add_library(weather_api ../slice/Demo/Weather.ice)
slice2cpp_generate(weather_api
  INCLUDE_DIRS ${CMAKE_CURRENT_SOURCE_DIR}/../slice
  HEADER_OUTPUT_DIR ${CMAKE_BINARY_DIR}/include
  INCLUDE_SCOPE PUBLIC)
target_link_libraries(weather_api PUBLIC demo_common)
```

`Weather.ice` includes `<Demo/Common.ice>`, so the generated `Weather.h` includes `<Demo/Common.h>`, which `demo_common`
generates in `${CMAKE_BINARY_DIR}/include/Demo` and publishes to `weather_api`. A target that links `weather_api` can
include both `Demo/Weather.h` and `Demo/Common.h`.

### Installing the Generated Headers

Install the generated headers with the CMake `install` command. Add `GENERATED_HEADERS` to the target's existing
`slice2cpp_generate` call to collect the absolute paths of the generated headers. When all headers belong in one
installation directory, install them with `install(FILES)`:

```cmake
slice2cpp_generate(weather_api INCLUDE_SCOPE PUBLIC GENERATED_HEADERS weather_api_headers)
install(FILES ${weather_api_headers} DESTINATION include/Demo)
```

`install(FILES)` puts every file directly in the destination, and a generated header includes the other generated
headers by their relative paths. When the headers are in subdirectories, install their root directory instead. In the
example of the previous section, both targets write their headers under `${CMAKE_BINARY_DIR}/include`:

```cmake
install(DIRECTORY ${CMAKE_BINARY_DIR}/include/ DESTINATION include)
```

The include directories that `INCLUDE_SCOPE PUBLIC` adds apply only in the build tree, so a target that you install and
export declares the installed include directory itself:

```cmake
target_include_directories(weather_api PUBLIC $<INSTALL_INTERFACE:include>)
```

### Result Variables

`find_package` sets the following variables:

| Variable                   | Description                                            |
| -------------------------- | ------------------------------------------------------ |
| `Ice_VERSION`              | The Ice version, such as `3.8.3`.                      |
| `Ice_SO_VERSION`           | The version of the Ice shared libraries, such as `38`. |
| `Ice_PREFIX`               | The installation prefix.                               |
| `Ice_INCLUDE_DIR`          | The directory of the Ice header files.                 |
| `Ice_SLICE_DIR`            | The directory of the Ice Slice files.                  |
| `Ice_SLICE2CPP_EXECUTABLE` | The path of the `slice2cpp` compiler.                  |

Use `Ice_SLICE2CPP_EXECUTABLE` where CMake does not evaluate generator expressions, such as in `execute_process` at
configure time.
